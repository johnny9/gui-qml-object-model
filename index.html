Bitcoin Core App (GUI QML) Object Model

A single-owner object hierarchy for the QML application: 6 roles + Core separated cleanly from lifetime scope, one feature-agnostic execution::Executor with fair-yielding SerialQueues, native handles confined to backend owners, and reverse-order shutdown.

One-Way DependenciesView → Controller → Contract ← Model. Models never know about pages or controllers.
Bounded ThreadsOne Executor (4 lanes) + 1 QmlInitExecutor thread + 1 payment-link QThread. Never scales with open wallets.
Confined Native Handlesinterfaces::Wallet & Handler stay in backend owners and are always freed off the UI thread.
Reverse-Order TeardownCancel prompts → drain features → appShutdown() → destroy Views/Models → flush DeferredDelete → join threads → destroy Core roots.

01 Roles, Scopes & Dependency Rules

Role defines what an object does. Scope (page, wallet, app) defines how long it lives. Keeping the two orthogonal avoids bloated god-models and forwarding wrappers.

RoleResponsibilityNaming RuleExamples
View QML layout, bindings, focus, dialogs, and navigation. Holds no request tickets, schedulers, or native handles. *.qml MainWindow.qml, SendCreate.qml, SendForm.qml, SendTransactionReview.qml
Controller Use-case state, prompts, busy/error state, and active operation handles. BitcoinQmlApplication::run is the composition root. *Controller, ShutdownCoordinator WalletController, WalletPageController, SendDraftController, TransactionReviewController
Interface Narrow abstract capability contract a controller depends on. Production models implement it; tests inject a fake. Capability contracts end in *Interface WalletAvailabilityInterface, SendDraftInterface, TransactionReviewInterface, SettingsEditorFactoryInterface
Model Observable domain data, drafts, item models, self-contained editors, or backend sessions. Outlives pages. *Model or concrete adapter name (no *Interface) WalletModel, SettingsModel, NodeModel, TransactionReviewModel, WalletSendDraft, walletopening::Session
Operation One async domain request with its own terminal state, result, and error, bound to its original target. Operation contracts end in *Operation SendOperation, PreparationOperation, FileSaveOperation, WalletSendHandle, walletsend::SendTask
Executor Bounded worker lanes, FIFO SerialQueues, and reserved off-UI cleanup. Knows nothing about wallets, settings, Qt/QML, or Core roots. execution::* (Internal C++) execution::Executor, execution::SerialQueue, execution::ValueCleanupQueue
Core Bitcoin Core native C++ backend interfaces (bitcoin/src/interfaces/). Always owned by backend C++ owners, never QML. interfaces::* NativeApplicationInterfaces, interfaces::Init, interfaces::Node, interfaces::Chain, interfaces::Wallet

Three Approved Dependency Paths

1. Workflow Coordination

View → Controller → narrow contract → Model / Session. Use an abstract *Interface where a test/capability seam helps, or an existing coherent facade such as WalletReceiveModel. Never invent forwarding controllers for symmetry.

2. Direct Presentation

View → Model / Controller. QML binds directly to observable data models (ActivityListModel, CoinsListModel, PeerListProxyModel) and controller state without intermediary copies.

3. Self-Contained Editors

View → EditorModel. Dedicated editor sessions (SettingsEditorModel, PaymentRequestEditorModel) own their draft, validation, and save lifecycle directly and retire cleanly when closed.

03 Execution & Cleanup Contract

The concurrency layer has only three small internal C++ primitives. All feature logic stays out of Executor.

execution::Executor & execution::SerialQueue

namespace execution {

enum class Lane { Core, Priority, Rpc, Utility };
enum class UtilityWorker { IO, Signer };

class SerialQueue {
public:
    bool post(std::function<void()> task);        // FIFO; yields after each task
    void close();                                 // Stops new posts to this queue only
    void whenDrained(std::function<void()> done); // Closed + empty + idle + 0 reservations
private:
    friend class ValueCleanupQueue;
    bool reserveCleanup();
    void cancelReservedCleanup();
    bool postReservedCleanup(std::function<void()> cleanup);
};

class Executor {
public:
    using Dispatch = std::function<bool(Lane, UtilityWorker, std::function<void()>)>;
    explicit Executor(Config config);             // Production worker threads
    explicit Executor(Dispatch dispatch);         // Deterministic manual/inline tests
    SerialQueue makeQueue(Lane, UtilityWorker = UtilityWorker::IO);
    void stopAndJoin();                           // Closes, drains, joins real workers
};

} // namespace execution

Key Runtime Invariants

  • Per-task yielding: SerialQueue::run() executes one task, destroys its captures outside the lock, and re-dispatches to the back of the lane worker if more tasks remain—preventing chunked jobs or large cleanup bursts from starving sibling queues (and staying O(1) stack on inline test dispatchers).
  • whenDrained() vs. Feature::stop(done): whenDrained() covers tasks on one queue. Session::stop(done) additionally disconnects handlers, runs optional wallet->remove(), and destroys unique_ptr<interfaces::Wallet> on Utility before reporting stopped.
  • Reserved teardown cleanup (ValueCleanupQueue): Uses private reserveCleanup() / postReservedCleanup() / postWithOutcome() so already-accepted retained values, native handles, and Core outcomes still finish on Utility even during Executor::stopAndJoin().
  • Injectable tests: Executor(Dispatch) runs the exact production SerialQueue with manual stepping. stopAndJoin() skips waitIdle() when no real workers exist so failed assertions never hang teardown.
  • Passive close() vs. explicit cancel(): Closing a queue stops new admissions without revoking already-supplied consent. Page dismissal revokes unclaimed send consent; once consent->claim() succeeds, the single Core send task finishes and records its real outcome.

Lifecycle guarantees:
  • Closing or unloading one wallet stops only its Session without affecting sibling wallets or recreating their pages.
  • If a wallet finishes loading after the app or destination closed, its unclaimed interfaces::Wallet and unload handler retire on Lane::Utility—never on the GUI thread.

Why two dedicated threads exist outside Executor:
  • QmlInitExecutor owns 1 internal std::thread running appInitMain(), subscription cleanup, and appShutdown() sequentially—keeping Lane::Core free for accepted settings writes during startup while preserving Core-thread cleanup affinity.
  • desktopintent::transport::Service owns 1 internal QThread strictly because QLocalServer and QLocalSocket require a live Qt event loop.

05 Concurrency & Shutdown Sequences

Time flows downward across thread lifelines. Every scenario preserves the invariant that native Core roots outlive all worker thread joins.

Orderly Application Shutdown (5 Steps)

Used on normal quit, early startup exit, and recoverable errors.

Native-Fatal Fast-Fail Path

Kept separate from orderly shutdown so a fatal Core error reports diagnostics and exits without hanging.
