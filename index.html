Bitcoin Core App (GUI QML) Object Model

Complete architecture of the gui-qml application—covering every major QML view, controller, interface, model, operation, and execution owner, stopping cleanly at the Bitcoin Core interfaces::* boundary.

One-Way DependenciesView → Controller → Contract ← Model. Models never know about pages or controllers.
Bounded ThreadsOne Executor (4 lanes) + 1 QmlInitExecutor thread + 1 payment-link QThread.
Strict Core BoundaryApp stops at interfaces::{Init, Node, Chain, Wallet, Handler} + ArgsManager—no Core internals.
Reverse-Order ShutdownCancel prompts → drain features → appShutdown() → destroy Views/Models → flush DeferredDelete → join threads → destroy Core roots.

01 Roles, Scopes & Dependency Rules

Role defines what an object does. Scope (page, wallet, app) defines how long it lives. Keeping them separate avoids god-models and redundant forwarding layers.

Three Approved Dependency Paths

1. Workflow Coordination

View → Controller → narrow contract → Model / Session. Use an abstract *Interface where a capability/test seam helps, or an existing coherent facade like WalletReceiveModel.

2. Direct Presentation

View → Model / Controller. QML binds directly to observable models (TransactionActivityModel, CoinsListModel, PeerListProxyModel, BlockClockModel) and controller state.

3. Self-Contained Editors

View → EditorModel. Dedicated editor sessions (SettingsEditorModel, PaymentRequestEditorModel) own their draft, validation, and retiring-while-saving teardown directly.

03 Execution & Cleanup Contract

All feature concurrency builds on three small internal C++ primitives in execution::.

execution::Executor & execution::SerialQueue

namespace execution {

enum class Lane { Core, Priority, Rpc, Utility };
enum class UtilityWorker { IO, Signer };

class SerialQueue {
public:
    bool post(std::function<void()> task);        // FIFO; yields after each task
    void close();                                 // Stops new posts to this queue only
    void whenDrained(std::function<void()> done); // Closed + empty + idle + 0 reservations
private:
    friend class ValueCleanupQueue;
    bool reserveCleanup();
    void cancelReservedCleanup();
    bool postReservedCleanup(std::function<void()> cleanup);
};

class Executor {
public:
    using Dispatch = std::function<bool(Lane, UtilityWorker, std::function<void()>)>;
    explicit Executor(Config config);             // Production worker threads
    explicit Executor(Dispatch dispatch);         // Deterministic manual/inline tests
    SerialQueue makeQueue(Lane, UtilityWorker = UtilityWorker::IO);
    void stopAndJoin();                           // Closes, drains, joins real workers
};

} // namespace execution

Key Runtime Invariants

  • Per-task yielding: SerialQueue::run() executes one task, destroys its captures outside the lock, and re-dispatches to the back of the lane worker if more tasks remain—so sibling queues interleave fairly without feature-level batch caps.
  • whenDrained() vs. Feature::stop(done): whenDrained() covers tasks on one queue. Session::stop(done) additionally disconnects handlers, runs optional wallet->remove(), and destroys unique_ptr<interfaces::Wallet> on Utility before reporting stopped.
  • Reserved teardown cleanup (ValueCleanupQueue): Uses private reserveCleanup() / postReservedCleanup() / postWithOutcome() so already-accepted values, native handles, and Core outcomes still finish on Utility during Executor::stopAndJoin().
  • Injectable tests: Executor(Dispatch) drives the real SerialQueue deterministically, discards stale rejected callbacks atomically, and skips waitIdle() in stopAndJoin() when no real workers exist.
  • Passive close() vs. explicit cancel(): Closing a queue stops new admissions without revoking already-supplied consent. Page dismissal withdraws unclaimed consent; once consent->claim() succeeds, the committed Core task finishes and records its outcome.
